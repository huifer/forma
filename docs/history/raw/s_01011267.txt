下面这篇按照微信公众号技术观点文章来写，保留标题的争议性，同时加入技术架构、代码示例和实际落地思路。核心不是否定 AI Coding，而是质疑当前 AI Coding 的生产方式。

<WritingBlock id="73182" variant="document"># 我认为 AI Coding 最大的骗局：让 AI 写代码

**100 万 Token，真正有价值的可能只有 1 万。我们是不是从一开始就用错了 AI？**

最近我一直在思考一个问题：

为什么我们已经拥有了如此强大的 AI，开发一个软件却依然需要消耗大量 Token？

让 AI 写一个页面，它会生成 HTML、CSS、React、TypeScript。

一个简单的管理后台，它可能生成几百个 div、几十个 class，外加各种组件、状态管理、数据请求、表单验证。

让它修改一个字段，它可能需要重新理解大量上下文，修改多个文件，再重新检查整个项目。

我们花费大量 Token，让 AI 做了很多事情。

但仔细想想，这些事情真的都需要 AI 来做吗？

div 需要 AI 写吗？

class 需要 AI 写吗？

CRUD 需要 AI 写吗？

表单验证需要 AI 每次重新实现吗？

数据库 Model、API 接口、页面布局，这些已经有明确规则的东西，为什么还要让 AI 一次又一次地生成？

**我越来越觉得，AI Coding 可能从一开始就走错了一个方向：我们让 AI 承担了太多本来不应该由它承担的工作。**

---

## 一、100 万 Token，真正有价值的内容有多少？

先想象一个场景。

你让 AI 开发一个用户管理系统。

需求其实很简单：

- 用户列表
- 用户新增
- 用户编辑
- 用户删除
- 用户状态管理
- 用户搜索
- 分页
- 权限控制

从业务角度看，真正需要思考的事情是什么？

1. 用户有哪些字段？
2. 用户之间有什么关系？
3. 哪些字段必须填写？
4. 哪些操作允许执行？
5. 不同角色拥有什么权限？
6. 页面需要展示哪些信息？

这些才是真正的业务需求。

但 AI Coding 的实际工作方式是什么？

它开始写：

```tsx
<div className="flex flex-col gap-4">
  <div className="flex items-center justify-between">
    <h1 className="text-xl font-semibold">
      User Management
    </h1>
    <button className="rounded-md bg-blue-500 px-4 py-2">
      Create User
    </button>
  </div>
  {/* 更多组件 */}
</div>
```

然后继续生成：

- CSS 样式
- React 组件
- TypeScript Interface
- API 请求
- CRUD 操作
- 表单校验
- 错误处理
- Loading 状态
- Empty 状态
- 各种 UI 细节

这里面有多少是业务创新？

又有多少是重复劳动？

我并不是说这些代码没有价值，而是说：

**这些代码绝大部分具有确定性，完全可以通过规则、模板和编译器生成。**

AI 最昂贵的能力应该用来解决不确定性，而不是反复生产确定性的内容。

---

## 二、我们为什么要让 AI 写代码？

我认为这与我们过去的软件开发思维有关。

以前，我们开发软件的过程是：

需求 → 设计 → 编码 → 编译 → 运行。

因此，当 AI 出现以后，我们很自然地把它放进了编码环节。

于是有了今天的 AI Coding：

人类描述需求，AI 理解需求，然后直接生成源代码。

但这里存在一个问题：

**源代码只是软件最终产物的一种表达形式，并不是软件本身的业务价值。**

我们真正需要的是一个能够正确运行的软件。

至于它内部使用多少个 div、多少个 class、多少个 React 组件，这些并不是用户真正关心的事情。

如果可以通过一个更精简、更稳定的中间描述，直接生成最终程序，为什么一定要让 AI 从头编写所有源代码？

这就引出了我想尝试的一种新模式。

---

## 三、不要让 AI 写代码，让 AI 生产 JSON / YAML

我的想法其实很简单：

**AI 负责描述软件，编译器负责生产软件。**

我们不再要求 AI 直接生成完整的 React、Vue、HTML 或者后端代码。

而是让 AI 只输出极少量结构化数据。

例如，还是刚才的用户管理系统。

AI 只需要生成这样的 YAML：

```yaml
app:
  id: user-manager
  name: User Manager

data:
  entities:
    User:
      fields:
        id:
          type: uuid
          primary: true

        name:
          type: string
          required: true

        email:
          type: email
          required: true
          unique: true

        status:
          type: enum
          values:
            - active
            - disabled

ui:
  pages:
    users:
      type: data-table
      entity: User

      columns:
        - name
        - email
        - status

      actions:
        - create
        - edit
        - delete

      filters:
        - status

logic:
  rules:
    - id: prevent-delete-active-admin

      when:
        user.role: admin
        user.status: active

      deny:
        action: delete
```

注意，这里没有 React。

没有 HTML。

没有 CSS。

没有 div。

没有 class。

甚至没有具体的 API 实现。

它只是描述：

- 我要什么数据结构。
- 我要什么页面。
- 页面展示什么字段。
- 用户可以做什么操作。
- 哪些业务规则必须遵守。

然后交给编译器。

编译器自动完成：

1. 创建数据库表。
2. 生成 ORM Model。
3. 生成 CRUD API。
4. 生成请求参数验证。
5. 生成 React 页面。
6. 生成 DataTable 组件。
7. 生成表单。
8. 生成权限控制。
9. 生成测试代码。
10. 生成构建和部署配置。

原本需要 AI 生成的大量代码，现在由确定性的程序完成。

**AI 只需要表达意图，不需要重复实现意图。**

---

## 四、真正需要的是一套 AI 软件编译器

这不是简单地把 JSON 转换成 HTML。

如果只是这样做，意义其实不大。

我认为真正的架构应该分成五层。

### 第一层：Specification Layer（规格描述层）

这是 AI 的主要工作区域。

AI 负责生成结构化规格：

- App DSL：应用结构。
- Data DSL：数据模型。
- UI DSL：界面描述。
- Logic DSL：业务规则。
- API DSL：接口定义。
- Workflow DSL：工作流。

AI 不应该随意创造字段和结构，而应该在预定义的 Schema 约束下生成内容。

### 第二层：Validation Layer（验证层）

AI 生成的 JSON 不一定正确。

所以必须进行严格验证：

- JSON Schema 验证。
- 字段类型验证。
- 引用关系验证。
- 组件属性验证。
- 业务规则验证。
- 权限规则验证。

不能通过验证的规格，不允许进入编译阶段。

### 第三层：AST / IR Layer（中间表示层）

这是整个系统最重要的部分。

不要让 YAML 直接生成 React。

而是先把 JSON/YAML 转换成统一的 AST 或 IR。

为什么？

因为 JSON/YAML 只是输入格式。

真正需要统一的是软件的语义结构。

例如，一个 DataTable 不应该只是一个 JSON 对象。

它应该在 IR 中拥有明确的语义：

- 数据来源是什么。
- 使用什么实体。
- 有哪些列。
- 有哪些操作。
- 依赖哪些权限。
- 关联哪些 API。
- 需要什么验证规则。

有了统一的 IR，后续才能支持多种编译目标。

### 第四层：Compiler Layer（编译层）

编译器负责把 IR 转换成真正的程序。

例如：

```text
                 Specification
                       |
                       v
                  Parser
                       |
                       v
                Schema Validator
                       |
                       v
                  Semantic Check
                       |
                       v
                    AST / IR
                       |
          +------------+------------+
          |            |            |
          v            v            v
       Frontend     Backend      Database
          |            |            |
          v            v            v
        React        Rust         MySQL
          |            |            |
          +------------+------------+
                       |
                       v
                 Executable App
```

同一份规格，可以编译成不同的技术实现。

比如：

- React。
- Vue。
- Kotlin。
- Swift。
- Rust。
- Node.js。

AI 不需要知道最终采用什么具体实现。

它只需要理解软件的业务语义。

### 第五层：Runtime Layer（运行时层）

并不是所有逻辑都应该在编译时生成。

对于动态权限、工作流、条件判断、事件处理等场景，可以提供统一 Runtime。

这样可以避免每次修改一个简单业务规则，都需要重新生成大量代码。

## 五、最重要的创新：AI 只允许修改 AST，不允许随意修改源代码

我认为这才是整个想法最值得深入研究的地方。

现在 AI Coding 最大的问题之一是：

修改一个很小的需求，可能导致大量代码变化。

例如：

用户希望把用户状态从：

```text
active / disabled
```

修改成：

```text
active / disabled / pending
```

传统 AI Coding 可能需要：

1. 找到 TypeScript 类型。
2. 找到数据库 Model。
3. 找到表单选项。
4. 找到状态展示组件。
5. 找到后端验证。
6. 找到相关测试。
7. 检查所有引用。

但如果采用规格驱动的方式呢？

AI 只需要修改：

```yaml
status:
  type: enum
  values:
    - active
    - disabled
    - pending
```

然后编译器通过依赖关系自动识别受影响的节点。

```text
User.status
     |
     +-- Database Schema
     |
     +-- ORM Model
     |
     +-- API Validation
     |
     +-- Form Options
     |
     +-- Table Renderer
     |
     +-- Test Cases
```

只重新编译受影响的部分。

而不是重新生成整个项目。

这意味着 AI 不需要每次都重新理解整个代码库。

它只需要理解当前规格，以及当前修改涉及的业务语义。

---

## 六、编译失败，也不应该让 AI 重写代码

还有一个非常现实的问题。

现在 AI Coding 经常出现这样的情况：

代码报错，然后把错误信息和大量代码交给 AI，让它重新修改。

修改之后，又出现新的错误。

于是进入循环。

如果采用规格驱动架构，错误反馈应该更加结构化。

例如：

```json
{
  "error": "INVALID_FIELD_REFERENCE",
  "path": "ui.pages.users.columns[2]",
  "expected": "Existing entity field",
  "actual": "user_status",
  "available": [
    "name",
    "email",
    "status"
  ]
}
```

AI 看到这个错误，只需要修改对应的字段。

不需要重新生成页面。

不需要重新生成组件。

更不需要重新生成整个项目。

这是一种非常重要的变化：

**从让 AI 修复代码，转变为让 AI 修复规格。**

修复范围越小，错误传播的概率就越低。

## 七、这套模式是不是适用于所有软件？

当然不是。

我不认为 JSON/YAML 可以替代所有编程语言。

复杂算法、实时系统、高性能计算、游戏引擎，以及一些高度复杂的交互逻辑，仍然需要传统代码。

我们不应该为了结构化而结构化。

我更看好以下领域：

| 软件类型 | 适用程度 |
|---|---|
| CRUD 管理后台 | 极高 |
| SaaS 标准业务系统 | 极高 |
| 内容管理系统 | 极高 |
| 数据大屏 | 极高 |
| 表单系统 | 极高 |
| API 服务 | 极高 |
| 工作流系统 | 极高 |
| 标准移动端应用 | 高 |
| 复杂交互应用 | 中 |
| 游戏引擎 | 低 |

对于无法通过 DSL 描述的复杂业务，可以提供受控的 Plugin、Extension 或 Native Code 接口。

核心原则是：

能通过确定性规则完成的事情，就不要让 AI 重复生成。

真正需要智能推理的部分，才交给 AI。

---

## 八、这并不是凭空想象，很多成熟技术早已证明这种思路可行

实际上，这种思想在软件工程中并不陌生。

例如：

**OpenAPI**

通过结构化规范描述 API，再生成不同语言的客户端和服务端代码。

**Protocol Buffers**

通过 `.proto` 文件定义数据结构，再通过编译器生成不同语言的代码。

**Terraform**

通过声明式配置描述基础设施的期望状态，再由执行引擎完成实际操作。

**Jsonnet**

通过可组合的数据配置，减少重复配置和模板代码。

**XState**

通过状态机描述复杂业务状态和转换逻辑。

这些技术分别解决了软件生产中的不同问题。

而我想探索的是：

能不能把这些思想进一步整合，建立一套面向 AI 的通用软件规格生成与编译体系？

让 AI 成为软件规格的生产者，让编译器成为软件的生产者。

---

## 九、我认为 AI Coding 的下一阶段，不应该是生成更多代码

现在行业都在讨论：

- 更强的 Coding Agent。
- 更大的上下文窗口。
- 更快的代码生成。
- 更多并行 Agent。
- 更强的自动调试能力。

这些当然有价值。

但我认为还应该有另一条路线：

**减少 AI 需要生成的内容。**

我们一直在想办法让 AI 写代码更快。

却很少有人认真思考：

能不能让 AI 根本不需要写那么多代码？

假设一个系统有 100 个页面。

每个页面都有大量重复的布局、表格、表单和交互。

传统方式下，AI 需要不断生成这些内容。

而在新的架构中：

100 个页面可能只需要 100 份精简的页面规格。

所有页面共享一套组件库、一套 Runtime、一套编译器。

AI 只负责描述差异。

剩下的全部交给确定性的程序。

这才是我认为更值得探索的方向。

---

## 最后

我并不认为未来程序员不再需要写代码。

我真正想表达的是：

**我们应该重新定义 AI 在软件生产中的位置。**

过去：

Human → AI → Source Code → Executable

未来可以尝试：

Human → AI → Specification → Compiler → Executable

AI 负责理解需求、抽象业务、设计结构、生成规则。

编译器负责类型检查、依赖分析、代码生成、构建和测试。

人类负责架构决策、复杂问题和最终质量。

这套体系如果真正成熟，可能会改变我们开发软件的方式。

毕竟，代码只是软件的表达形式。

业务逻辑才是软件真正的价值。

**当一段代码已经可以被确定性地生成，我们为什么还要浪费昂贵的智能去重复生产它？**

这可能是我对 AI Coding 最想提出的一个质疑。

你认为未来 AI 应该继续直接写代码，还是应该转向生成结构化规格，由编译器完成软件生产？
