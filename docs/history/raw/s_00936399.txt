# 五、DSL 设计：不要一开始创造一门通用编程语言

这里我想做一个重要的技术决策：

**不要尝试用 JSON/YAML 描述整个世界。先做一套受约束的软件描述语言。**

它应该像 OpenAPI 一样规范，像 Terraform 一样声明期望状态，像 Protobuf 一样可以编译，像 SQL 一样有清晰的语义。

## 5.1 DSL 分层设计

我建议采用一个核心协议 + 六个领域 DSL。

| DSL | 文件后缀 | 描述范围 | 优先级 |
|---|---|---|---|
| AppSpec | `.app.yaml` | 应用、模块、导航 | P0 |
| DataSpec | `.data.yaml` | 实体、字段、关系 | P0 |
| UISpec | `.ui.yaml` | 页面、组件、交互 | P0 |
| LogicSpec | `.logic.yaml` | 条件、规则、计算 | P1 |
| APISpec | `.api.yaml` | 接口、请求、响应 | P1 |
| WorkflowSpec | `.flow.yaml` | 事件、节点、执行流程 | P2 |

第一版不要实现六个完整语言。

建议先完成：

- AppSpec
- DataSpec
- UISpec

LogicSpec 第一阶段只支持简单规则。

API 可以从 DataSpec 派生 CRUD 接口。

Workflow 留到后续。

这样可以避免 DSL 本身变成一个巨大项目。

## 5.2 具体设计

**AppSpec：应用描述**

```yaml
spec_version: "1"

app:
  id: task-manager
  name: Task Manager
  version: 1.0.0

modules:
  - id: users
  - id: tasks

navigation:
  type: sidebar
  items:
    - module: users
    - module: tasks

targets:
  frontend: react
  backend: typescript
  database: sqlite
```

**DataSpec：数据模型描述**

```yaml
spec_version: "1"

entities:
  User:
    fields:
      id:
        type: uuid
        primary: true

      name:
        type: string
        required: true
        max_length: 100

      email:
        type: email
        required: true
        unique: true

      status:
        type: enum
        values:
          - active
          - disabled

    indexes:
      - fields:
          - email
```

**UISpec：页面描述**

```yaml
spec_version: "1"

pages:
  users:
    route: /users
    title: Users

    layout:
      type: page

    components:
      - id: user-table
        type: data-table

        source:
          entity: User

        columns:
          - field: name
          - field: email
          - field: status

        actions:
          - type: create
          - type: edit
          - type: delete

      - id: user-form
        type: form

        entity: User

        fields:
          - name
          - email
          - status
```

这里有一个关键约束：

`type: data-table` 是编译器认识的语义组件，而不是一个任意的 React 组件名称。

编译器知道 DataTable 的完整实现。

AI 只需要提供字段、数据源和操作。

## 5.3 不允许自由创造组件

建议建立组件注册中心。

```text
components/
├── layout/
│   ├── Page
│   ├── Sidebar
│   └── Header
│
├── data/
│   ├── DataTable
│   ├── DataGrid
│   └── DataView
│
├── forms/
│   ├── Form
│   ├── Input
│   ├── Select
│   └── DatePicker
│
├── feedback/
│   ├── Dialog
│   ├── Toast
│   └── EmptyState
│
└── charts/
    ├── LineChart
    ├── BarChart
    └── PieChart
```

每个组件都有：

- 唯一 ID。
- 版本号。
- 属性 Schema。
- 默认行为。
- 类型定义。
- 生成规则。
- 测试。
- 依赖关系。

例如：

```json
{
  "component": "DataTable",
  "version": "1.0",
  "props": {
    "entity": {
      "type": "EntityRef",
      "required": true
    },
    "columns": {
      "type": "FieldRef[]",
      "required": true
    },
    "pagination": {
      "type": "PaginationConfig"
    }
  }
}
```

这样，AI 无法随意编造一个 `DataTableV99`，也不能传递一个编译器不认识的属性。

## 5.4 DSL 必须具备版本兼容性

这点不能省略。

假设以后 DataSpec 从 v1 升级到 v2。

不能要求用户重新生成所有项目。

需要：

```text
Spec v1
   |
   v
Migration Engine
   |
   v
Spec v2
   |
   v
Validator
   |
   v
Compiler
```

建议借鉴 Buf 的 Schema Lint、Breaking Change Detection 和版本兼容机制。它已经证明了结构化规格不仅可以生成代码，还可以对接口变化进行自动审查。<Cite refs={["turn167470search0","turn167470search2","turn167470search4"]}/>

# 六、AST / IR：真正决定技术上限的部分

如果说 DSL 是 AI 和编译器之间的语言，那么 IR 就是编译器真正理解的软件模型。

我的建议是：

**一个 Canonical IR，不要为每个 Agent、每种 DSL 建立一套独立 AST。**

## 6.1 IR 应该包含什么？

```text
IR
├── Project
│   ├── Modules
│   └── Targets
│
├── Data
│   ├── Entities
│   ├── Fields
│   ├── Relations
│   └── Indexes
│
├── UI
│   ├── Pages
│   ├── Layouts
│   ├── Components
│   └── Events
│
├── Logic
│   ├── Rules
│   ├── Conditions
│   └── Actions
│
├── API
│   ├── Endpoints
│   ├── Requests
│   └── Responses
│
└── Dependencies
    ├── References
    ├── Imports
    └── BuildGraph
```

每一个节点必须有稳定 ID。

例如：

```json
{
  "id": "field:user.status",
  "kind": "DataField",
  "type": "enum",
  "owner": "entity:user",
  "attributes": {
    "values": [
      "active",
      "disabled"
    ]
  },
  "source": {
    "file": "spec/data/user.data.yaml",
    "path": "$.entities.User.fields.status"
  }
}
```

注意 `source`。

它是后续实现可追踪生成、错误定位和增量编译的基础。

## 6.2 IR 必须有类型系统

不能只做一个任意 JSON Object。

建议支持：

| 类型 | 示例 |
|---|---|
| Primitive | string、number、boolean |
| Entity | User、Order |
| FieldRef | User.email |
| ComponentRef | DataTable |
| EventRef | onSubmit |
| Relation | User hasMany Order |
| Condition | status == active |
| Action | create、update、delete |
| Expression | amount * quantity |

还需要检查：

- 类型是否兼容。
- 引用是否存在。
- 依赖是否循环。
- 操作是否合法。
- 是否存在权限冲突。
- 组件是否支持对应数据类型。

## 6.3 建立 Dependency Graph

例如：

```text
User.status
    |
    +---- DatabaseSchema
    |
    +---- ORMModel
    |
    +---- APIValidator
    |
    +---- UserForm
    |
    +---- UserTable
    |
    +---- UserTests
```

修改 `User.status` 后，编译器只需要重新处理相关节点。

但这里要避免一个技术误区：

不能仅根据文件名决定哪些代码需要重新生成。

应该根据 IR 节点、生成器依赖和构建产物的真实依赖建立 DAG。

建议为每个节点维护：

```text
node_id
input_hash
dependency_hash
compiler_version
generator_version
output_hash
```

使用内容寻址缓存。

只有输入、依赖或生成器版本发生变化，才需要重新生成。

## 6.4 确定性编译

这里的确定性不能只理解为相同 YAML 得到相同文件。

应该是：

\[
Output = Compile(IR, CompilerVersion, GeneratorVersion, Dependencies)
\]

相同的输入、编译器、生成器和依赖版本，应该得到相同的输出。

需要做到：

- 稳定节点排序。
- 稳定文件排序。
- 固定代码格式。
- 固定依赖版本。
- 消除时间戳等不确定因素。
- 固定代码生成模板。
- 构建环境可复现。
- 生成物可校验。

Buf 的工程实践很值得借鉴：它把格式化、Lint、Breaking Change Detection、依赖管理和代码生成整合进统一工具链，并强调生成结果的确定性。<Cite refs={["turn167470search3","turn167470search5","turn167470search6"]}/>

# 七、Compiler：不要做一个简单的模板引擎

我建议将编译器拆成四个阶段。

<box border radius="lg" padding={3} gap={3}>
  <box gap={1}>
    **Phase 1 · Frontend Compiler**

    <text color="secondary" size="xs">解析 JSON/YAML、Schema、DSL、语义检查</text>
  </box>
  <divider color="subtle"/>
  <box gap={1}>
    **Phase 2 · Semantic Compiler**

    <text color="secondary" size="xs">IR 构建、类型检查、依赖解析、规则检查</text>
  </box>
  <divider color="subtle"/>
  <box gap={1}>
    **Phase 3 · Target Compiler**

    <text color="secondary" size="xs">IR 转换为不同技术栈的目标代码</text>
  </box>
  <divider color="subtle"/>
  <box gap={1}>
    **Phase 4 · Build Compiler**

    <text color="secondary" size="xs">依赖解析、构建、测试、产物校验</text>
  </box>
</box>

## 7.1 Target Compiler

第一阶段只支持一个目标。

我建议：

<badge color="success">首个目标</badge>

**React + TypeScript + Hono + SQLite**

理由：

- React 适合验证 UI DSL。
- TypeScript 适合构建全栈业务应用。
- Hono 轻量，方便生成服务端代码。
- SQLite 适合本地开发和低成本部署。
- 后续可以增加 MySQL 等数据库 Target。

不要第一天支持 React、Vue、Svelte、Angular、Kotlin、Swift、Rust。

这会让生成器维护成本失控。

## 7.2 生成代码的所有权

建议将项目文件分成三类：

| 文件区域 | 所有权 | 是否允许 Agent 直接修改 |
|---|---|---|
| spec/ | 规格系统 | 通过 Spec 操作修改 |
| generated/ | 编译器 | 不允许直接修改 |
| extensions/ | 开发者 | 允许正常编码 |

例如：

```text
project/
├── spec/
│   └── ...
│
├── generated/
│   ├── frontend/
│   ├── backend/
│   ├── database/
│   └── types/
│
└── extensions/
    ├── services/
    ├── algorithms/
    └── custom-components/
```

这是非常重要的边界。

如果 Agent 修改了 generated 中的代码，下一次编译就可能覆盖它。

所以必须建立：

- 生成文件标记。
- 写入拦截。
- Hash 校验。
- 生成差异报告。
- 自定义扩展接口。

不能通过简单的禁止写入来解决全部问题，因为有些项目确实需要人工修改生成代码。

可以提供 `adopt` 操作，把人工修改提取为扩展，或者让 Agent 将修改迁移到对应 Spec。

## 7.3 Plugin Compiler

未来最有价值的不是一个巨大的 Compiler，而是一个 Compiler Plugin Ecosystem。

例如：

```text
plugins/
├── frontend/
│   ├── react
│   ├── vue
│   └── svelte
│
├── backend/
│   ├── hono
│   ├── express
│   └── rust-axum
│
├── database/
│   ├── sqlite
│   ├── mysql
│   └── postgres
│
└── integrations/
    ├── stripe
    ├── auth
    └── storage
```

但插件不能随意修改 IR。

必须通过稳定的 Plugin API 注册：

- 新的 Target。
- 新的 Component。
- 新的 Generator。
- 新的 Validator。
- 新的 Runtime Provider。

插件版本也必须进入构建指纹。

# 八、Runtime：不要把所有逻辑都编译成静态代码

我建议采用：

**Compile-time Generation + Runtime Execution 的混合架构。**

两种机制各有职责。

| 机制 | 负责什么 |
|---|---|
| 编译时 | 数据模型、API、类型、页面骨架、静态规则 |
| 运行时 | 动态权限、条件、事件、工作流、可配置行为 |

例如：

用户权限规则：

```yaml
permissions:
  User:
    read:
      roles:
        - admin
        - operator

    delete:
      roles:
        - admin
      conditions:
        - field: status
          operator: equals
          value: disabled
```

编译器负责验证权限表达式，并生成对应的执行计划。

Runtime 负责根据当前用户和数据执行权限判断。

这里需要特别注意：

**不能因为 AI 生成了权限 DSL，就认为系统已经安全。**

必须在服务端强制执行权限，不能只依赖前端隐藏按钮。

Runtime 还应该提供：

- 类型安全的数据访问。
- 参数验证。
- 事件执行。
- 事务管理。
- 权限检查。
- 审计日志。
- 错误处理。
- 超时和资源限制。

对于自定义逻辑，第一版允许调用受控 TypeScript Extension，不建议一开始设计完整的通用脚本语言。

# 九、可靠性体系：这是产品真正的护城河

我认为你最应该投入研发资源的地方不是 DSL，而是 Reliability。

一个系统可以生成 JSON，不代表它能够稳定生产软件。

真正的挑战是：

- AI 是否修改了错误的节点？
- 是否遗漏了依赖？
- 是否破坏了已有功能？
- 是否出现生成物漂移？
- 是否引入了安全漏洞？
- 是否能在失败后回滚？

我建议建立七层可靠性体系。

## 9.1 七层保障

| 层级 | 检查内容 |
|---|---|
| L1 Protocol | 操作格式、权限、参数 |
| L2 Schema | 字段、类型、结构 |
| L3 Semantic | 引用、关系、业务规则 |
| L4 Dependency | 依赖图、循环依赖、影响范围 |
| L5 Generation | 生成文件、Hash、覆盖冲突 |
| L6 Build & Test | 编译、单测、集成测试 |
| L7 Runtime | 权限、行为、执行结果 |

每次 Spec 变更都必须生成一个 Change Set。

例如：

```json
{
  "change_id": "chg_001",
  "status": "validated",
  "operations": [
    {
      "operation": "node.update",
      "target": "data.entities.User.fields.status"
    }
  ],
  "impact": {
    "affected_nodes": 6,
    "affected_files": 8
  },
  "checks": {
    "schema": "passed",
    "semantic": "passed",
    "dependency": "passed",
    "breaking_change": "warning"
  }
}
```

然后进入 Preview 阶段。

Agent 和用户都能看到本次修改会影响哪些文件。

## 9.2 Transactional Build

这是我认为必须做的功能。

不要让编译器边生成边覆盖原文件。

建议：

```text
Spec Change
    |
    v
Validate
    |
    v
Build Plan
    |
    v
Temporary Output
    |
    v
Build & Test
    |
    +---- Failed ----> Discard
    |
    v
Compare Output
    |
    v
Atomic Apply
    |
    v
Record Snapshot
```

如果生成失败：

- 保留旧版本。
- 丢弃不完整输出。
- 保存错误信息。
- 返回对应 Spec 节点。
- 不允许半成品污染工作目录。

## 9.3 Breaking Change Detection

例如原来：

```yaml
email:
  type: string
```

修改为：

```yaml
email:
  type: integer
```

不能只看 YAML 是否有效。

必须识别这是一个可能破坏现有数据和接口的变更。

建议设置：

- Safe Change
- Compatible Change
- Breaking Change
- Destructive Change

对于数据库字段删除、类型变更、API 删除等操作，必须提供迁移计划。

借鉴 Buf 的 Schema Compatibility 检查机制，不要等到生产环境才发现协议变化破坏了调用方。<Cite refs={["turn167470search0","turn167470search10"]}/>

## 9.4 Agent 权限控制

我建议设计三个权限级别。

| 权限 | 行为 |
|---|---|
| Read | 读取 Spec、IR、编译报告 |
| Propose | 提交 Spec Patch、预览变更 |
| Apply | 应用通过验证的变更 |

默认：

- AI 可以读取。
- AI 可以提交修改建议。
- AI 不可以绕过验证直接覆盖生成产物。
- 删除数据、执行迁移、部署等高风险操作需要单独授权。

## 9.5 可靠性不能只依靠 AI 自己验证

AI 生成的测试也可能有错误。

因此必须有独立于生成 Agent 的验证器。

例如：

AI 生成一个用户删除功能。

验证系统不应该只检查：

```text
AI says: Tests passed.
```

而应该真正执行：

1. 删除接口是否存在。
2. 无权限用户是否无法删除。
3. 删除不存在的用户是否返回正确错误。
4. 关联数据是否按预期处理。
5. 数据库事务是否正确。
6. 生成的 API 是否与规格一致。

**AI 负责提出实现，独立验证器负责证明实现符合规格。**

这才是可靠性架构。

# 十、Agent 工作流：Codex、Claude Code、Pi 怎么使用它？

我不建议你重新做一套 Agent。

让已有 Agent 继续负责：

- 理解用户需求。
- 任务规划。
- 业务分析。
- 复杂算法。
- 原生代码开发。

你的系统只接管结构化软件生产。

## 10.1 理想工作流

<box border radius="lg" padding={3} gap={2}>
  <title size="lg">Agent + Compiler 协作</title>
  <list connector="solid" marker="number" gap={2}>
    <list-item>
      **用户提出需求**

      创建一个用户管理系统。
    </list-item>
    <list-item>
      **Agent 理解需求**

      将需求拆成数据、页面、业务规则。
    </list-item>
    <list-item>
      **Agent 调用 Spec Protocol**

      创建 User Entity、Users Page。
    </list-item>
    <list-item>
      **Compiler 验证**

      Schema、类型、语义、依赖检查。
    </list-item>
    <list-item>
      **Compiler 预览**

      展示变更节点和受影响文件。
    </list-item>
    <list-item>
      **执行代码生成**

      生成数据库、API、页面。
    </list-item>
    <list-item>
      **独立验证**

      Build、Test、Security Check。
    </list-item>
    <list-item>
      **反馈 Agent**

      成功返回构建摘要，失败返回结构化错误。
    </list-item>
  </list>
</box>

## 10.2 不同 Agent 的接入策略

| Agent | 第一阶段接入 | 后续 |
|---|---|---|
| Codex | CLI + MCP | 专用 Adapter |
| Claude Code | MCP + Skills | Hooks |
| Pi | CLI + Extension | 深度集成 |
| 其他 Agent | MCP | Generic Adapter |

这里的目标不是让所有 Agent 都能理解你的内部实现。

而是让所有 Agent 只需要掌握一个协议。

## 10.3 MCP 工具设计

建议第一版提供以下工具：

```text
spec_get
spec_search
spec_apply_patch
spec_validate
spec_get_ir
spec_preview
spec_compile
spec_verify
spec_rollback
```

每个工具都返回精简结构化结果。

例如：

```json
{
  "success": false,
  "error": {
    "code": "FIELD_NOT_FOUND",
    "path": "pages.users.columns[2]"
  },
  "repair": {
    "suggested_operation": "node.update",
    "available_fields": [
      "name",
      "email",
      "status"
    ]
  }
}
```

不要把整个项目的 IR、所有生成文件和完整构建日志都塞回 Agent 上下文。

只返回：

- 变更结果。
- 受影响节点。
- 关键错误。
- 下一步建议。

详细日志保存在本地。

这样才能真正减少上下文污染。

# 十一、最重要的产品创新：Spec Patch，而不是 Spec Rewrite

我想把这个功能单独提出来。

普通 Spec-Driven Development 的流程，往往是：

```text
需求
  ↓
生成完整规格
  ↓
修改完整规格
  ↓
重新执行工作流
```

我们应该采用：

```text
Current Spec
     |
     v
Semantic Diff
     |
     v
Minimal Patch
     |
     v
Validation
     |
     v
Incremental Compilation
```

例如：

用户说：

> 用户管理页面增加一个手机号字段。

Agent 不需要重新输出整个 User Entity。

只需要：

```json
{
  "operation": "node.create",
  "target": "data.entities.User.fields",
  "value": {
    "phone": {
      "type": "string",
      "required": false
    }
  }
}
```

编译器只需要分析与手机号有关的影响范围。

可能生成：

- 数据库迁移。
- ORM 字段。
- API 类型。
- 表单字段。
- 表格列（如果规格要求）。
- 对应测试。

而其他模块完全不需要重新生成。

这可以成为产品最核心的交互方式。

# 十二、技术选型：我建议 Rust 做核心，TypeScript 做目标运行时

结合这个项目的定位，我不建议纯 TypeScript 实现所有东西，也不建议一开始全用 Rust。

我的最终推荐是双语言架构。

## 12.1 技术栈

| 模块 | 技术 | 决策 |
|---|---|---|
| Compiler Core | Rust | 核心引擎 |
| CLI | Rust / clap | 本地入口 |
| Parser | serde_yaml + serde_json | 规格解析 |
| Schema Validation | jsonschema | 结构验证 |
| IR | Rust 自定义类型 | 统一语义模型 |
| Dependency Graph | petgraph | DAG |
| Hash | BLAKE3 | 内容指纹 |
| Local Storage | SQLite | 构建状态 |
| Protocol | JSON-RPC / MCP | Agent 接口 |
| Runtime | TypeScript | 动态业务逻辑 |
| Frontend Target | React + TypeScript | 首个目标 |
| Backend Target | Hono | 首个目标 |
| Database Target | SQLite | 首个目标 |
| Testing | Vitest + Playwright | 自动化验证 |
| Build | Vite + TypeScript | 目标项目构建 |

其中 JSON Schema 验证可以使用 Rust 的 `jsonschema` crate，已经具备多版本 Schema 支持和结构化验证能力。<Cite refs={["turn167470search1","turn167470search13"]}/>

## 12.2 为什么 Rust 做 Compiler Core？

因为核心引擎需要：

- 严格类型系统。
- 可预测的执行过程。
- 并行编译。
- 高效的依赖图处理。
- 文件系统操作。
- 内容寻址缓存。
- 稳定的 CLI。
- 跨平台分发。

Rust 非常适合这类基础设施。

而 TypeScript 负责生成的应用运行时，可以让目标项目更容易接入现有 Web 开发生态。

## 12.3 不建议的技术路线

不要：

1. 用 LLM 参与编译器核心决策。
2. 用 Prompt 代替 Schema。
3. 用正则表达式解析复杂代码。
4. 把所有 DSL 写成一个巨大的 YAML。
5. 让 AI 自己决定组件名称。
6. 每次修改都重新生成整个项目。
7. 让 Compiler 直接覆盖用户代码。
8. 在第一版实现多语言多平台编译。
9. 把编译器做成一个依赖云端的 SaaS。
10. 先做漂亮的可视化编辑器。

先把命令行和编译链路做正确。
