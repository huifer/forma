# 二十一、真正值得长期投入的三个研究方向

如果这个项目要做成长期基础设施，我认为还应该关注三个未来方向。

### 方向 A：从代码 AST 进化为 Software Semantic Graph

传统 AST 主要描述源代码语法。

但我们需要的是更高层次的业务语义图。

例如：

```text
User
  |
  +-- hasMany --> Order
  |
  +-- owns ----> Permission
  |
  +-- exposes -> API
  |
  +-- renders -> UserTable
  |
  +-- validates -> UserForm
```

AI 不需要阅读几百个文件才能知道用户实体与哪些功能相关。

它可以直接读取语义图。

这是跨 Agent 共享项目理解能力的重要基础。

### 方向 B：从 Code Generation 进化为 Software Change Management

不要只关心如何生成软件。

还要关心软件在长期变化中如何保持正确。

例如：

- 一个需求变更会影响什么？
- 哪些 API 可能发生破坏性变化？
- 哪些数据库迁移不安全？
- 哪些测试需要重新执行？
- 哪些模块可以复用缓存？
- 哪些变更需要人工审批？

未来可以把 SpecForge 做成软件变更的控制平面。

### 方向 C：让 Agent 具备结构化的软件操作能力

现在 Agent 的主要操作方式是：

```text
Read File
Edit File
Write File
Run Command
```

未来可以增加：

```text
Create Entity
Update Field
Add Component
Connect Relation
Define Rule
Preview Change
Compile Target
Verify Result
```

这意味着 Agent 不再只是一个可以操作文件的程序员。

它还可以成为一个能够操作软件结构的工程师。

# 二十三、我给你的最终创业判断

我认为这个方向值得做，但需要非常清楚地认识到一个事实：

**Spec-Driven Development 本身不是创新，Compiler 也不是创新。**

把结构化规格、语义编译、增量生成、多 Agent 协议和独立验证整合成一套开发者真正愿意使用的基础设施。

## 我的最终建议：先不要开发完整产品，先验证一个核心假设

我建议你接下来直接做一个非常小的实验：

**用 100 个 JSON 节点，生成一个完整的 Task Manager。**

然后让 Codex、Claude Code、Pi 分别修改这个项目。

观察三个问题：

1. 它们是否都能准确操作同一份 Spec？
2. 修改一个节点，是否能准确识别所有受影响的代码？
3. 是否能够在不重新生成整个项目的情况下，持续交付正确的软件？

如果这三个问题都能解决，你就不只是在做一个代码生成器，而是在建立一套新的 AI 软件生产基础设施。

**我最看好的最终产品不是 AI 写代码，而是 AI 驱动的确定性软件生产系统。**

这才是 SpecForge 应该追求的方向。

---

*最后一个重要提醒：不要把「AI 输出 JSON」当成产品护城河。真正值得投入的是语义模型、编译正确性、变更影响分析、增量构建和独立验证。JSON 只是入口，编译器才是产品。*
